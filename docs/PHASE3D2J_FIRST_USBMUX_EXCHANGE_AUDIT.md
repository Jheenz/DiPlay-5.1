# Phase 3D.2J - First USBMUX protocol exchange audit

## Scope, hardware baseline and conclusion

**STATIC/CODE AUDIT ONLY.** No device opened or claimed, USB transfer sent,
USBMUX host executed, pairing record accessed or native QDrive code executed
during J. No runtime behavior, connection gate, version label or APK changed.
Phase 3D.2K is **design only**, not implemented.

The user reports real-E01 [Phase 3D.2I](PHASE3D2I_ACTIVE_CONFIG5_USBMUX_CLAIM_TEST.md)
PASS: direct 05AC:12A8 without Carlinkit, five configurations, active 5,
configuration 5 USBMUX ID 1/alt 0/255.254.2 with bulk OUT 0x04/IN 0x85, same-connection
GET_CONFIGURATION=5, claim=true with force=false, release=true, cleanup success,
and zero bulk/interrupt transfers.
**ACTIVE CONFIGURATION 5 USBMUX INTERFACE CLAIM CONFIRMED**.
This is user-supplied hardware evidence, not a USBMUX packet capture.

**The smallest identifiable exchange is one 20-byte version request and its
version 2 reply, stopping before setup07.** It can prove USBMUX protocol
communication, not full transport initialization/TCP readiness. Setup07 is a
separate later packet, emitted only after a version reply is validated.
Neither source nor native code makes it a prerequisite for receiving that reply.
There is no need to connect62078, send a plist, access pairing records or start
an Apple service to test this prefix.

Current `Iap2UsbMuxHost.open()` cannot serve as that prefix-only test: it
unconditionally sends setup07 and starts a persistent reader after the reply.
A future K boundary must be isolated from that opener and from orchestration.
The normal connection gate remains false; no automatic startup is authorized.

### First OUT transfer

Actual logical packet generated by DiPlay:

```text
00 00 00 00  00 00 00 14  00 00 00 02  00 00 00 00  00 00 00 00
```

- Total 20 bytes; on the real scoped USBMUX **bulk OUT 0x04**.
- `begin` passes `handshakeTimeoutMillis` to `pipe.write`.
- Normal default: 60000ms OUT budget; direct diagnostic: 5000ms.
- `Iap2UsbSession.write` delegates to
  [UsbTransferCompatibility.writeFully](../shared/src/main/java/com/shilapi/xcertplay/transport/UsbTransferCompatibility.kt),
  line130, then connection.bulkTransfer at line355 of session source.
- API22 per-call cap 16KiB; 20 fits one initial Android OUT call.
- A positive short write triggers **additional calls for the unsent suffix**
  under the write deadline. Zero/negative stops; a final non20 total fails.
  This is not a resend of the whole request, but is more than exactly one
  transfer when a short write occurs. K must explicitly reject a short OUT
  instead of using this continuation policy.
- No explicit ZLP or controlTransfer is sent by DiPlay's version write.

### First IN transfer

`takeFrame` calls `pipe.read(remainingHandshakeMillis)` **after OUT returns**.
`Iap2UsbSession.read` creates UsbRequest, initializes **bulk IN0x85**, queues
a direct buffer, and waits for completion. It is bulk traffic even though
the IN path is asynchronous `UsbRequest`, not `bulkTransfer`.

- Buffer=min(65536,platform transfer cap), therefore **16384 bytes on API22**.
- On API22: legacy `queue(buffer,length)` and blocking `requestWait()`;
  [awaitUsbRequest/await](../shared/src/main/java/com/shilapi/xcertplay/transport/UsbTransferCompatibility.kt),
  lines60/84, schedule cancellation at timeout.
- On API26+: timed requestWait is used; canceled-request completion may be
  drained by `drainCancelledRead`, session line457, with1000ms extra cleanup
  wait. This is **cancellation cleanup**, not QDrive's pre-handshake IN drain.
- API22 scheduled cancellation does not give a hard kernel wall-clock guarantee;
  requestWait must respond to cancellation. Do not call this inherently
  nonblocking or assume modern timeout APIs exist on E01.
- IN handshake deadline starts **after** OUT. Normal read budget60000ms,
  direct read budget5000ms. They are separate budgets, not a combined total.
- During handshake the first `read` uses remaining handshake budget, not the
  later reader poll1000ms/default or500ms/direct.

Current opener may perform multiple IN calls to assemble fragments/coalesced
frames, repeat no-completion polls within deadline, and discard up to32 stale
TCP/protocol6 frames. It does not resend the version request. Other unexpected
frames or more stale frames fail. This permissive behavior must not be silently
inherited by a one-response K test.

## 2. First-packet framing and expected reply

### Actual initial wire structure

This is the **direct Apple USBMUX device protocol**, not the local usbmuxd
client/socket framing (length/version/type/tag with different encoding).
Do not send a usbmuxd Listen/Connect plist or a little-endian16-byte
daemon-client header to endpoint04.

The initial packet has an **8-byte base header plus 12-byte version payload**:

| Offset | Width | Endianness/value | Meaning |
|---|---|---|---|
| 0 | 4 | BE0 | Protocol selector: VERSION. This is not version number2. |
| 4 | 4 | BE20 (`0x14`) | Total logical packet length, including header. |
| 8 | 4 | BE2 | Version payload major. |
| 12 | 4 | BE0 in request | Version payload minor. |
| 16 | 4 | Zero in request | Version payload padding/reserved. |

No independent message tag, nonce, request ID, magic, TCP port or mux sequence
is carried by this initial8-byte header. Offset8 is **major**, not FEEDFACE.
There is no authentication/certificate material in these generated bytes.

DiPlay's generic incremental receive abstraction always exposes16 header
bytes and a4-byte payload for a length20 packet; it reads word8 as version2
and bytes12-13 as `frame.sequence`. For the **initial** packet, those bytes
overlap the high half of the wire version minor field. That is a local parser
representation, not evidence of a wire transaction tag or v2 sequence in the
initial header. QDrive/upstream parse it with8-byte header while not negotiated.

After v2 negotiation, outbound protocol2/6 uses a16-byte mux header:
BE protocol,BE length,BE FEEDFACE,BE16 tx-sequence,BE16 receive acknowledgment,
followed by setup payload or TCP header/data.

### Exact expected IN contract, not a guaranteed byte-for-byte echo

DiPlay accepts a complete logical frame iff:

```text
readBE32(0) == 0
readBE32(4) == 20
readBE32(8) == 2
```

It does **not** require minor0, trailing zeros, FEEDFACE or a particular
incoming sequence. Therefore an expected reply shape is:

```text
00 00 00 00  00 00 00 14  00 00 00 02  mm mm mm mm  pp pp pp pp
```

`mm` and `pp` are recorded payload bytes, not assumed zero/credentials.
Zero in both yields the same20 bytes as the request, but **echo equality is
not the implemented validator**. Protocol1 is CONTROL, not "version reply."

[UsbMuxFrameBuffer](../shared/src/main/java/com/shilapi/xcertplay/transport/UsbMuxFrameBuffer.kt),
line23, waits for16 header bytes, validates declared length16..65536, then
waits for complete declared length and consumes that many bytes. It retains
all remainder. `begin` adds the exact protocol/20/version2 checks above.

### Important extra-data limitation

Existing [replay regression](../shared/src/test/java/com/shilapi/xcertplay/transport/UsbMuxIssue100RegressionTest.kt),
line191, includes a previously captured24-byte completion with declared
length20. DiPlay accepts the first20 and buffers the extra4. Its optional
padding logic only discards those4 later if a particular valid TCP header at
offset4 qualifies; padding-only data is retained. This is **not an E01 first
reply capture**, and does not prove that E01 replies will be20,24 or split.

K should initially require **one IN completion of exactly20 bytes**, validating
the fields above. A24-byte completion or fragmented/short completion is an
explicit unexpected-extra/short-response STOP, even if a valid20-byte prefix
exists. Do not declare optional padding harmless, discard it, scan for a
header or connect to TCP merely to make padding recovery work. Such a STOP
would provide evidence for a later static reassessment, not authorize retries
or broader traffic.

## 3. setup07: separable follow-up, not Lockdown

DiPlay's `sendFrame(PROTOCOL_SETUP, byteArrayOf(0x07))` produces17 bytes:

```text
00 00 00 02  00 00 00 11  FE ED FA CE  00 00  AA AA  07
```

- Protocol2 SETUP, length17,16-byte negotiated header, one-byte body07.
- Tx sequence0 initially; `AA AA` derives from `takeFrame`'s incoming
  `frame.sequence`. With zero minor bytes, DiPlay sends ACK0000.
- OUT04; write timeout2000ms. `sendFrame` increments nextTxSequence after
  successful write.
- This is a **bulk USBMUX setup packet**, not a USB endpoint0 SETUP transaction,
  vendor control request or Lockdown plist.
- No dedicated setup acknowledgment is awaited by `begin`. Immediately afterward
  it starts the reader thread and returns; no TCP service is automatically
  connected by the host itself.
- QDrive also sends protocol2/body07 after receiving version2, but resets
  tx0/receiveFFFF. **Its setup packet is not byte-identical to DiPlay's**:
  `00 00 00 02 00 00 00 11 FE ED FA CE 00 00 FF FF 07`.

The sources establish setup as the normal negotiated-v2 initialization
continuation before TCP/service use. They do not document bit-level meanings
of07 or prove that every iOS release tolerates omitting it for later TCP.
Do not call it a Pair/Trust command, flags with guessed semantics, or a reset
guaranteed to restore the previous state.

**Stopping after the version response is valid as a bounded diagnostic prefix.**
The reply has already arrived before setup can be sent. Omitting setup does
not invalidate evidence of the first exchange; it intentionally leaves the
normal v2 initialization incomplete. Therefore:

- PASS may say **USBMUX PROTOCOL COMMUNICATION CONFIRMED**.
- Report **VERSION EXCHANGE ONLY — SETUP07/TCP/LOCKDOWN NOT TESTED**.
- Do **not** say full transport established, TCP ready or full QDrive init
  reproduced. If full transport readiness were the goal, setup would belong
  in a separately authorized broader phase. It is not K's proposed goal.

Cross-check only (not a substitute for local native evidence):
[upstream usbmuxd device.c](https://github.com/libimobiledevice/usbmuxd/blob/3ded00c9985a5108cfc7591a309f9a23d57a8cba/src/device.c)
defines VERSION0/CONTROL1/SETUP2/TCP6,8-byte initial header,12-byte version
payload; `device_version_input` decodes major1/2, sends setup07 for2, then marks
active and starts preflight work. Its `send_packet` resets setup tx0/rxFFFF.
This explains naming and corroborates the recovered sequence, not a promise
that running upstream usbmuxd would avoid pairing. **Do not run that daemon.**

- First version OUT async timeout**0** at0x95378 (no transfer timeout), not200ms.
  Immediate submit error propagates; initialization tests negative at0x93E86.
  No first-version resend loop was found in this recovered path.
- OUT completion callback0x95470 logs status at0x954AA onward, frees/removes

- Normal async IN timeout**0**; successful completion re-submits the read via

## 5. QDrive pre-read/drain: what is proved and what is not

Exact call arguments assembled at0x95F3E-0x95F56:

```text
libusb_bulk_transfer(existingHandle, storedInEndpoint, stackBuffer,
                     4096, &actualLength, 200)
```

Stored IN is85 for config5. PLT0x78E9C -> GOT0x2CE78C
`libusb_bulk_transfer:0xA0EC4`. The wrapper invokes sync helper0xA0EE0,
fills transfer timeout200 at0xA0F28, submits at0xA0F3C and waits for completion
via0xA0E5C/0xA0F4C. It pumps libusb events until callback completion; this is
**synchronous/blocking to the caller with a200ms transfer timeout**, not an
unbounded timeout0 read. Event-pump/cancel scheduling still prevents a strict
CPU wall-clock assertion from static code alone.

At0xA0F50 it writes actualLength and maps status through table0x2779E0:
completed0 -> return0; timeout status2 -> **-7**; error/cancel -> -1;
stall -> -9; no-device -> -4; overflow -> -8.

At0x95F5A-0x95F5C QDrive tests **return code**, not actualLength:

- Return0 -> repeat the same4096/200ms drain.
- Any nonzero -> exit drain and continue toward version send.
- Successful short read or zero-length completion still repeats.
- Timeout is treated as end-of-drain. Errors/disconnect/submit failure are
  likewise not distinguished here and do **not** stop registration immediately.
- Drain bytes are discarded, not parsed into a pending version/TCP response.
- **The overall loop has no bound on read count or total duration.** Continuous
  successful data/ZLP can keep it running despite each read's timeout.

Operational purpose is clear from control flow: empty previously queued IN
data before starting a fresh mux registration/version request. The historical
reason and necessity for this E01 state are **not proven**. It could be stale
prior-session data, but this code alone cannot identify the drained bytes.
Do not turn that explanation into a hardware fact.

DiPlay does **not** pre-drain before its version OUT; it discards up to32 stale
TCP frames only after sending. Neither pattern proves a drain is needed for
the current real E01: E/G/I user results contain zero prior bulk traffic.
They also do not prove the endpoint has no unsolicited pending bytes.

**Recommendation: do not reproduce the drain in first K.**
It would add one or more reads, consume unexplained data, conflate timeout with
other errors and obscure first-exchange evidence. An unexpected first reply is
a STOP, not an invitation to drain/retry.
Public Android API has no non-consuming "peek pending endpoint data" operation.
Without a pre-read, pending data can only be detected from returned response/
extra bytes, not categorically ruled out before OUT. A later drain experiment
would need separate authorization and bounded accounting; J adds none.

## 7. Proposed Phase 3D.2K - one bounded version request/response

**Design only; do not run or implement as part of J.**

### Preconditions and isolated access

- No Carlinkit; exactly one permitted Apple device, exact 05AC:12A8.
  Require existing permission; never request it.
- Exactly five configurations; unique configuration ID 5 containing case-sensitive
  Valeria interface-name evidence, USBMUX 255/254/2 and CDC-NCM 2/13/0, 10/0/1.
- Actual **configuration 5** object, unique USBMUX ID 1/alt 0; exact bulk OUT 0x04
  and IN 0x85, positive inventoried maxPacketSizes; do not use flattened index 13.
- For a strict one20-byte transfer profile, require endpoint maxPacketSizes
  **greater than20**, and IN maxPacketSize<=1024 for the proposed1024-byte IN
  buffer. Unexpected sizes STOP rather than adding ZLP/fragment policy.
- Open fresh device once; same-handle standard GET_CONFIGURATION80/08/0/0,
  length1/1000ms must return count1,value5. Revalidate identity/layout/permission.
- Claim exactly once with **force=false**; proceed only if true.
- Keep other DiPlay USB operations and other USB applications stopped;
  record whether E/G/I were the only preceding operations and that they sent
  no bulk. No assumption that reconnecting preserved active5.

Future boundary should expose only one-shot read-active, claim, version OUT,
response IN, release, close and passive state observation. No generic host/
TCP connect, Pair/session/service clients, bulk session reader thread,
setter/vendor/alternate/native bypass or pairing-record APIs.
Reuse scoped I validation, not a transport opener or the normal controller.

### Exact minimal traffic and budgets

1. After successful claim, log request bytes/endpoint/timestamp.
2. **One public API22 synchronous bulkTransfer OUT 0x04** of the exact 20-byte request
   above, proposed timeout **1000ms**. Require returned count 20.
   No suffix write, whole-packet retry, ZLP or setup.
3. **One public API22 synchronous bulkTransfer IN 0x85** with a 1024-byte buffer,
   proposed timeout **1000ms**. This is a read capacity, not a request that the
   phone send 1024 bytes. Require returned count **20**.
   A20-byte device short packet can complete this larger buffer; it avoids
   deliberately truncating24-byte/coalesced data to make a prefix look valid.
4. Decode only returned bytes as BE; require protocol 0, total 20, major 2.
   Record minor and reserved word as metadata; do not require an echo of zeros
   or treat version minor bytes as an acknowledgment tag.
5. Never emit setup07, start reader thread, accept/discard32 stale TCP frames,
   accumulate short responses, follow returned ports, retry or fall back to
   Lockdown. Exactly **one response transfer maximum**.
6. Observe detach/state changes passively; any event/inventory discrepancy
   suppresses PASS. No re-enumeration reopen or reclaim.
7. Finally release exactly the claimed object once if claimtrue, record result;
   close in nested finally regardless of failure/cancellation/release result.
   No protocol-level disconnect/reset/restore during cleanup.
8. Save complete report and STOP.

Two 1000ms transfer budgets are an intentional **bounded diagnostic design**
deviation from normal DiPlay 5/60s budgets and native async timeout 0, not
recovered QDrive constants. No protocol evidence requires retransmission;
a timeout is a STOP outcome, not proof iPhone lacks USBMUX.
API22 bulkTransfer reports negative failure generically; do not label every
negative IN result definitively "timeout" without elapsed/state evidence.
Use `IN_TIMEOUT_OR_TRANSFER_FAILURE` where the public API cannot distinguish.
Run off UI thread; public claim/release have no timeout argument. Cancellation
blocks later traffic but must not skip cleanup.

### PASS contract and limitations

Require exact preconditions/active5/scoped claimtrue, OUT count20, one IN count20,
valid protocol0/length20/major2, stable device/configuration-scoped inventory,
no cancellation, releasetrue and cleanup success:

```text
USBMUX PROTOCOL COMMUNICATION CONFIRMED
VERSION EXCHANGE ONLY — SETUP07/TCP/LOCKDOWN NOT TESTED
```

Report request/response counts, fields and at most the bounded version packet
bytes, all timings, events, cleanup and **setup packets=0, TCP connects=0,
Lockdown requests=0**. Do not expose pairing records/keys/certificates.
Do not persist unknown oversized/TCP/plist payloads: log counts and bounded
header metadata for unexpected data, not arbitrary authentication traffic.

The initial version packet has **no transaction nonce/tag**. If a prior
identical version reply was already pending, a matching packet cannot be
cryptographically/time-correlated to this OUT by its fields alone.
PASS proves that this run sent the known request and read a valid USBMUX
version packet over the verified endpoints; it must not overclaim freshness
against other apps/prior sessions. Controlled no-prior-bulk history reduces
this risk but does not prove the endpoint empty. No silent pre-drain is proposed.

Likewise one IN read cannot prove there are no bytes still queued afterward.
It only rejects extra bytes delivered in that completion; no follow-up read is
added to broaden the phase.
